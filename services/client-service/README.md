# client-service

Клиентская база: карточка клиента, контакты, программа лояльности.

| | |
|---|---|
| **Язык** | Python 3.11 + FastAPI |
| **БД** | PostgreSQL, `client_db` |
| **Транспорт** | REST наружу, gRPC в обе стороны, публикация в RabbitMQ |
| **Деплой (ПР7)** | Serverless-контейнер в Яндекс.Облаке |

Первый сервис, который одновременно и gRPC-сервер, и gRPC-клиент.

## Ответственность

**Владеет:** личными данными клиента, контактами, предпочитаемым каналом связи,
балансом и историей начисления баллов.

**Не владеет:** историей записей — она принадлежит `booking-service`, который эти
записи и создаёт. Карточка подтягивает историю по gRPC, а не хранит копию.

Баллы начисляет не сам сервис: `billing-service` после оплаты вызывает
`AddLoyaltyPoints`, потому что сумму знает он. Здесь только хранение и правило
начисления — 5% от оплаченной суммы, округление вниз.

## REST API

| Метод | Путь | Что делает |
|---|---|---|
| `POST` | `/clients` | Завести клиента |
| `GET` | `/clients?phone=` | Поиск по телефону — основной сценарий на ресепшене |
| `GET` | `/clients/{client_id}` | Карточка: своё состояние + история записей из `booking` |
| `GET` | `/clients/{client_id}/loyalty` | Баланс и история начислений |

`GET /clients/{client_id}` — тот самый эндпоинт с вложенными вызовами из требований
ПР6: внутри обработчика идёт gRPC-запрос в `booking`.

## gRPC

**Сервер**, `proto/mirea/client/v1/client.proto`:

| Метод | Кто вызывает | Зачем |
|---|---|---|
| `GetClientContacts` | notification | Телефон, email, предпочитаемый канал |
| `AddLoyaltyPoints` | billing | Начислить баллы после оплаты счёта |

**Клиент:** `booking.ListClientAppointments` — история записей для карточки.

## Идемпотентность начисления

`invoice_id` уникален в `loyalty_entries`. Биллинг может повторить вызов при ретрае,
но баллы начислятся один раз: повторный вызов вернёт `points_added = 0` и текущий
баланс. Гонку двух одновременных ретраев разрешает уникальный индекс.

Проверено на живой системе: три вызова с одним `invoice_id` дали 260, 0, 0.

## События

Публикует `client.registered`. Ничего не потребляет.

## Как устроен код

Раскладка ровно как у `core-service` и `catalog-service`. Из девяти файлов `infra/`
восемь совпадают байт в байт, отличается только `config.py`.

В каркас в этом сервисе добавились две вещи, полезные всем:

- `infra/grpc_client.py` — вызов соседа с прокидыванием трассы в метаданные
  и переводом чужих кодов в свои: `NOT_FOUND` соседа становится нашим
  `NotFoundError`, недоступность — `UnavailableError` и 503 наружу.
- `AppContext.clients` — слот для gRPC-клиентов сервиса. Каркас про их устройство
  ничего не знает, только закрывает на выходе.

## Запуск

```bash
docker compose up -d client-service   # REST :8005, gRPC :9005
```

## Тесты

По ПР8 — unit и интеграционные, 14 штук.

**Unit** — расчёт баллов, включая округление вниз и нулевые суммы.

**Интеграционные** — против настоящего Postgres в базе `client_db_test`:
регистрация с публикацией события, запрет дубля телефона, поиск, идемпотентность
начисления по `invoice_id`, накопление баланса.
