# billing-service

Деньги за визит: счёт после завершённой записи, оплата, комиссия специалиста.

| | |
|---|---|
| **Язык** | Python 3.12 + FastAPI |
| **БД** | PostgreSQL, `billing_db` |
| **Транспорт** | REST наружу, gRPC-клиент к `booking` и `client`, потребление и публикация RabbitMQ |
| **Порты** | REST :8006 |
| **Автотестов** | 29 |

Первый Python-сервис, который потребляет события: до него консьюмер был только
в Go (`inventory`).

## Ответственность

**Владеет:** счетами, платежами, расчётом комиссии специалиста.

**Не владеет:** ценой услуги и деталями визита (`booking`), балансом баллов
клиента (`client`). Сумму знает биллинг, поэтому он и инициирует начисление
баллов — но хранит их не он.

Реального эквайринга нет, оплата отмечается вручную: это учебный проект.

## Основной сценарий

```
appointment.completed (RabbitMQ)
  → gRPC booking.GetAppointment(appointment_id)   # услуга, специалист, цена
  → выставить счёт, посчитать комиссию (40% от суммы)
  → publish invoice.issued

POST /invoices/{id}/pay
  → gRPC client.AddLoyaltyPoints(client_id, invoice_id, сумма)
  → publish invoice.paid
```

Событие несёт только `appointment_id`, детали биллинг запрашивает сам. Тонкие
события плюс запрос за деталями — сознательный выбор: payload не разрастается
и не приходится версионировать его при каждом изменении карточки визита.

## REST API

| Метод | Путь | Что делает |
|---|---|---|
| `GET` | `/invoices/{invoice_id}` | Счёт |
| `POST` | `/invoices/{invoice_id}/pay` | Отметить оплату |
| `GET` | `/branches/{branch_id}/invoices` | Счета филиала, фильтр по статусу |
| `GET` | `/employees/{employee_id}/commission` | Комиссия специалиста за период |

`POST /pay` — эндпоинт с вложенными вызовами: внутри обработчика
идёт gRPC-запрос в `client`.

Комиссия считается **только по оплаченным счетам**: выставленный, но не оплаченный
счёт комиссию не порождает.

## Идемпотентность

Два независимых уровня:

- **Inbox `processed_events`** — повторная доставка `appointment.completed` не
  выставит второй счёт. Отметка пишется той же транзакцией, что и счёт: иначе
  упавшая обработка оставила бы событие помеченным, и повтор молча пропустил бы его.
- **`appointment_id` уникален в `invoices`** — страховка на уровне схемы, даже если
  inbox по какой-то причине не сработает.

Начисление баллов идемпотентно на стороне `client-service` по `invoice_id`, так что
повтор `POST /pay` баллы не задвоит.

## Каркас

В `infra/` добавился `consumer.py` — потребитель RabbitMQ для Python-сервисов:
prefetch 16, продолжение трассы из `EventEnvelope.traceparent`, `reject` без повтора
в dead-letter, ack на неизвестный ключ чтобы очередь не вставала. Устройство то же,
что в Go-версии.

## Запуск

```bash
docker compose up -d billing-service   # REST :8006
```

## Тесты

Два вида: unit и интеграционные.

**Unit** — расчёт комиссии, включая округление и свойство «комиссия не больше суммы».

**Интеграционные** — против настоящего Postgres в базе `billing_db_test`:
выставление счёта с публикацией события, игнорирование дубля события, откат
транзакции снимает и отметку в inbox, запрет повторной оплаты, отчёты по филиалу
и комиссии с фильтром по периоду.
