# gateway

Единственная точка входа в систему: проверка JWT и маршрутизация в сервисы.

| | |
|---|---|
| **Язык** | Python 3.12 + FastAPI |
| **БД** | нет |
| **Транспорт** | REST наружу, REST внутрь, OIDC с Keycloak |
| **Порты** | REST :8000 — единственный, открытый наружу |
| **Автотестов** | 50 |

> Инфраструктурный компонент. **В счёт восьми микросервисов не идёт** — своей
> предметной области у него нет.

## Зачем он есть

Ядром системы задуман `core-service`, но проксировать через него чужие запросы —
плохая идея: релиз ядра положил бы всю систему, а на трассировке каждый запрос
проходил бы через ядро дважды. Это ровно тот распределённый монолит, за который
микросервисную архитектуру и ругают.

Поэтому роли разделены. Шлюз — тонкий, без бизнес-логики: аутентификация и
маршрутизация. `core-service` остаётся центром в более сильном смысле — как
единственный источник правды об организации, к которому синхронно ходят остальные.

## Почему написан руками, а не взят готовый

Готовый шлюз с OIDC-плагином (Traefik, Kong, Envoy) спрятал бы всё интересное
внутри конфигурации: получение ключей, проверку подписи, разбор claims. Здесь это
около восьмидесяти строк явного кода, которые видно и можно покрыть тестами.

Второй довод практический: аутентификация — самая муторная часть на отладке, и
держать её на том же языке, что и ядро, дешевле, чем прыгать между стеками.

Python был бы неверным выбором при терминации TLS, ограничении частоты запросов
или тысячах запросов в секунду — ничего из этого здесь нет. В боевой системе
такого масштаба разумнее взять Envoy или Traefik с плагином OIDC.

## Что делает с запросом

1. Ищет путь в маршрутной таблице. Незнакомый путь — 404, знакомый с чужим
   методом — 405 с заголовком `Allow`.
2. Проверяет токен: подпись ключом realm, срок, издателя, получателя и клиента.
3. Сверяет роль пользователя с требованиями маршрута.
4. Проксирует запрос в сервис, прокидывая личность в заголовках.

Проверяется весь набор, а не только подпись: токен с верной подписью, но выданный
другим realm или другому клиенту, — это чужой токен. Отдельно отбрасывается
ID-токен: подпись и realm у него те же, отличается `typ`.

```
POST /auth/token          логин и пароль в обмен на токен (для отладки)
GET  /routes              маршрутная таблица с требуемыми ролями
GET  /healthz /readyz     живость и готовность
* /...                    всё остальное уходит в сервисы
```

`POST /auth/token` существует только потому, что фронтенда нет. В боевой системе
браузер идёт в Keycloak сам по authorization code с PKCE, и пароль до шлюза
не доходит вовсе.

## Роли

| Роль Keycloak | Права |
|---|---|
| `admin` | Всё, включая оплату счетов, цены и управление филиалами |
| `manager` | Клиенты, записи, склад, отчёты филиала |
| `specialist` | Расписание, закрытие визитов, комиссия, прайс |

Полная таблица — в `app/routing/table.py` и на `GET /routes`.

**Шлюз проверяет роль, но не принадлежность объекта.** Что специалист смотрит
своё расписание, а не чужое, решать должен сервис — шлюз не знает, чей это визит,
и знать не должен. Для этого сервису и приезжает идентификатор пользователя.
Сейчас сервисы его получают и кладут в события, но проверок владения не делают:
для них нужна связь между пользователем Keycloak и сотрудником в `core-service`,
которой пока нет. Это ближайшее продолжение работы, а не забытая деталь.

## Проброс личности

После шлюза сервисы общаются по gRPC, и личность нужно нести дальше — иначе
внутренняя сеть оказывается доверенной целиком: кто попал внутрь периметра,
действует от любого имени.

| | |
|---|---|
| `X-User-Id` | `sub` из токена — идентификатор пользователя Keycloak |
| `X-User-Name` | `preferred_username`, закодирован процентами |
| `X-User-Roles` | роли realm через запятую |

Те же три заголовка едут дальше в метаданных gRPC. Одноимённые заголовки,
пришедшие снаружи, затираются: иначе личность подделает любой, кто знает их
названия. Сам токен внутрь не идёт — за периметром он уже проверен.

Дальше личность попадает в поле `actor` конверта события: в шине видно, чьё
действие привело к событию. У событий, порождённых обработкой другого события,
поле пустое — там нет человека.

## Настройка

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `GATEWAY_OIDC_ISSUER` | `http://localhost:8080/realms/mirea` | ожидаемый `iss` в токене |
| `GATEWAY_OIDC_INTERNAL_URL` | пусто | адрес Keycloak изнутри сети |
| `GATEWAY_OIDC_AUDIENCE` | `mirea-api` | ожидаемый `aud` |
| `GATEWAY_OIDC_CLIENT_ID` | `mirea-web` | ожидаемый `azp` |
| `GATEWAY_<СЕРВИС>_URL` | `http://localhost:800X` | адрес сервиса |

Адресов Keycloak два, и это не дублирование: в токене стоит тот адрес, по которому
Keycloak видел браузер (`localhost`), а ключи шлюз забирает изнутри сети
(`keycloak:8080`). Проверять `iss` надо против публичного.

## Грабли, на которые уже наступили

- **Keycloak подставляет в `iss` адрес запроса.** Токен, полученный шлюзом
  изнутри сети, оказывается «от другого издателя», чем токен из браузера, и
  проверка `iss` их не сводит. Лечится `KC_HOSTNAME` в `docker-compose.yml`:
  издатель становится фиксированным независимо от того, кто спрашивает.
- **Без маппера `audience` в токене нет `aud` вовсе**, и проверка получателя
  превращается в фикцию. Маппер добавлен в `deploy/keycloak/mirea-realm.json`.
- **Без маппера `realm roles` роли не попадают в токен**, и шлюзу нечего
  проверять — все запросы становятся 403.
- **Без заполненного `email` и пустого `requiredActions`** пользователь из
  realm-импорта получает `Account is not fully set up` вместо токена.

Первые две ломались молча и выглядели как ошибка в коде проверки, поэтому на них
есть интеграционные тесты против живого Keycloak — `tests/integration`.

## Как проверить руками

```bash
docker compose up -d

TOKEN=$(curl -s -X POST localhost:8000/auth/token \
  -H 'Content-Type: application/json' \
  -d '{"username":"owner","password":"owner"}' | jq -r .access_token)

curl -s localhost:8000/routes | jq '.[0:3]'
curl -s localhost:8000/templates                            # 401
curl -s localhost:8000/templates -H "Authorization: Bearer $TOKEN"
```

Учётные записи realm: `owner/owner` (admin), `admin-tverskaya/manager` (manager),
`specialist-anna/specialist` (specialist).
