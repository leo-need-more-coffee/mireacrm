# booking-service

Запись клиентов к специалистам: расписание, свободные слоты, жизненный цикл визита.

| | |
|---|---|
| **Язык** | Go 1.26 + chi + pgx |
| **БД** | PostgreSQL, `booking_db` |
| **Транспорт** | REST наружу, gRPC в обе стороны, публикация в RabbitMQ и NATS |
| **Порты** | REST :8003, gRPC :9003 |
| **Автотестов** | 34 |

## Ответственность

**Владеет:** записями (appointments), занятостью слотов, историей визитов.

**Не владеет:** графиком специалиста (`core-service`), длительностью и ценой услуги
(`catalog-service`). Оба справочника спрашиваются синхронно в момент записи.

Go здесь по существу: захват слота — конкурентная операция, два администратора могут
записывать на одно время одновременно. Слот берётся под транзакцией с уникальным
ограничением на `(employee_id, time_range)`.

## REST API

| Метод | Путь | Что делает |
|---|---|---|
| `GET` | `/branches/{branch_id}/slots` | Свободные слоты на дату с фильтром по услуге и специалисту |
| `POST` | `/appointments` | Записать клиента |
| `GET` | `/appointments/{id}` | Детали записи |
| `POST` | `/appointments/{id}/complete` | Специалист закрывает визит |
| `POST` | `/appointments/{id}/cancel` | Отмена записи |

`POST /appointments` — самый нагруженный сценарий системы: внутри обработчика идут
два gRPC-запроса (в `core` за графиком специалиста, в `catalog` за длительностью
услуги), и только потом захватывается слот.

## gRPC

**Сервер**, `proto/booking.proto`:

| Метод | Кто вызывает | Зачем |
|---|---|---|
| `GetAppointment` | billing | Детали визита по `appointment_id` из события |
| `ListClientAppointments` | client | История записей для карточки клиента |

**Клиент:** `core.GetEmployeeSchedule`, `core.GetBranch`, `catalog.GetService`.

## События

**Публикует в RabbitMQ:** `appointment.created`, `appointment.cancelled`,
`appointment.completed`.

`appointment.completed` — ключевое событие системы, его слушают сразу трое:
`inventory` списывает расходники, `billing` выставляет счёт, `analytics` считает выручку.

**Публикует в NATS:** `mirea.branch.{id}.schedule` при любом изменении занятости.
Это живое табло на ресепшене — открытые интерфейсы гасят слот мгновенно, без опроса
сервера. Гарантии доставки не нужны: клиент ресинкнется при переподключении.

## Как устроен код

```
cmd/booking/main.go     сборка и запуск
internal/
├── infra/              каркас — переносится в другой Go-сервис без правок
├── booking/            предметная область: models, slots, service, repository
├── api/                HTTP: router, dto
├── rpc/                gRPC: server, mapping
└── clients/            gRPC-клиенты к core и catalog
migrations/             SQL + //go:embed
```

Раскладка та же, что у Python-сервисов, только в идиомах Go: `cmd/` и `internal/`
вместо пакета `app`. Граница каркас/домен там же — `infra/` ни от кого не зависит,
домен не знает о транспортах.

## Гонка за слот

Два администратора могут жать «записать» одновременно. Проверка занятости перед
вставкой оставлена, но конфликт решает **база**: ограничение `EXCLUDE USING gist`
по `(employee_id, tstzrange(starts_at, ends_at))`. Условие
`WHERE status IN ('scheduled','completed')` означает, что отменённая запись
слот освобождает, а завершённая — держит.

Репозиторий распознаёт конфликт по имени ограничения и отдаёт `ErrSlotTaken`,
домен превращает его в 409. Проигравший гонку получает внятный ответ, а не 500.

## Сетка расписания

Слоты выравниваются по `SlotStep` (30 минут). Смена с 9:10 даёт первый слот в 9:30 —
иначе расписание рассыпается на неиспользуемые огрызки. Запись должна уместиться
целиком в одну смену: растянуть её через перерыв нельзя.

## Образ

Multi-stage на `distroless/static`, **34 МБ** против 332 у Python-сервиса. Холодный
старт в десятки миллисекунд, поэтому сервис подходит для бессерверного развёртывания.

В distroless нет ни shell, ни curl, поэтому healthcheck контейнера выполняет сам
бинарник: `/booking -healthcheck` дёргает свой же `/readyz`.

## Запуск

```bash
docker compose up -d booking-service   # REST :8003, gRPC :9003
```

Миграции накатываются на старте через `goose` из встроенной `//go:embed`-файловой
системы: отдельный бинарник и монтирование каталога не нужны.

## Тесты

Два вида: unit и интеграционные.

```bash
go test ./...                    # только unit, база не нужна
go test -tags=integration ./...  # плюс интеграционные, нужен Postgres
```

**Unit** — доменная логика на фейках: сетка слотов, пересечение интервалов,
попадание записи в смену, перевод проигранной гонки в конфликт.

**Интеграционные** (12 шт.) — против настоящего Postgres в базе `booking_db_test`.
Схема поднимается миграциями, а не `CREATE TABLE` в тесте: так проверяются и они.

Вынесены под сборочный тег `integration`, чтобы `go test ./...` без базы оставался
быстрым, а в CI база поднималась отдельным шагом.

Покрыто то, что фейками проверить нельзя, потому что логика живёт в SQL:
срабатывание `EXCLUDE` на пересечении, освобождение слота при отмене и удержание
при завершении, встык как не-пересечение, keyset-пагинация по `(starts_at, id)`
и различение «записи нет» от «не тот статус».

DSN тестовой базы переопределяется переменной `BOOKING_TEST_POSTGRES_DSN`.
