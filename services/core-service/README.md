# core-service

Ядро системы: единственный источник правды об организации. Кто такая компания, какие
у неё филиалы, кто в них работает, на какой должности и по какому графику.

| | |
|---|---|
| **Язык** | Python 3.12 + FastAPI |
| **БД** | PostgreSQL, `core_db` |
| **Транспорт** | REST наружу, gRPC-сервер внутрь, публикация в RabbitMQ |
| **Порты** | REST :8001, gRPC :9001 |
| **Автотестов** | 40 |

## Ответственность

**Владеет:** компаниями, филиалами, сотрудниками, должностями, графиками работы специалистов.

**Не владеет:** записями клиентов (`booking-service`), клиентской базой (`client-service`),
услугами и прайсом (`catalog-service`). Ядро отвечает на вопрос «кто и где работает»,
а не «что происходит».

Роль центра означает, что к нему синхронно ходят почти все остальные сервисы.
Маршрутизацией чужих запросов ядро при этом не занимается — это дело `gateway`.

## REST API

| Метод | Путь | Что делает |
|---|---|---|
| `POST` | `/companies` | Зарегистрировать компанию (сеть салонов) |
| `POST` | `/companies/{company_id}/branches` | Открыть филиал |
| `POST` | `/branches/{branch_id}/employees` | Принять сотрудника, назначить должность и график |
| `GET` | `/branches/{branch_id}/employees` | Сотрудники филиала |
| `GET` | `/employees/{employee_id}/schedule` | График работы специалиста на период |

## gRPC

Сервер, `proto/core.proto`:

| Метод | Кто вызывает | Зачем |
|---|---|---|
| `GetBranch` | booking, analytics | Проверить существование филиала, получить название |
| `GetEmployeeSchedule` | booking | Работает ли специалист в запрошенное время |
| `ListEmployees` | analytics | Справочник сотрудников для отчётов |

## События

Публикует в `mirea.events`: `branch.opened`, `employee.hired`.

Ничего не потребляет — ядро находится в начале цепочки, состояние организации
меняют только люди через API.

## Как устроен код

REST и gRPC живут в одном процессе и одном event loop — один контейнер на сервис.
Бизнес-операции лежат в `app/domain.py` и вызываются обоими транспортами, поэтому
логика не дублируется.

```
app/
├── __main__.py     python -m app
├── main.py         сборка приложения и запуск
│
├── infra/          каркас — копируется в другой сервис без правок
│   ├── config.py     настройки (меняется только префикс переменных)
│   ├── db.py         фабрики движка и сессий
│   ├── errors.py     доменные исключения
│   ├── events.py     издатель в RabbitMQ
│   ├── lifespan.py   AppContext: ресурсы процесса
│   ├── pagination.py курсоры
│   └── rpc.py        перехватчик ошибок, разбор аргументов, сборка сервера
│
├── models.py       предметная область
├── commands.py     входные команды, общие для обоих транспортов
├── domain.py       бизнес-операции
│
├── api/            HTTP
│   ├── deps.py
│   ├── schemas.py    представления домена в ответах
│   ├── companies.py
│   └── employees.py
│
└── rpc/            gRPC
    ├── mapping.py    представления домена в protobuf
    └── servicer.py
```

Правило копирования читается из дерева: `infra/` не трогаешь, всё остальное
переписываешь под свою предметную область.

Зависимости идут в одну сторону: `infra/` не знает ни о ком, домен не знает о
транспортах, транспорты знают о домене. Проверяется грепом по импортам.

Ресурсы процесса — движок БД и издатель событий — собираются в `AppContext` на
старте и живут в состоянии приложения. Модули ничего не создают при импорте: иначе
`import app.infra.db` открывал бы пул соединений в unit-тестах и в `alembic`,
а подменить настройки после импорта было бы нельзя.

Сессию БД оба транспорта получают одинаково, через `AppContext.session()`.

**Команды и представления разделены.** `commands.py` — то, что домен принимает на
вход, одинаково от REST и от gRPC. Представления наружу у каждого транспорта свои:
`api/schemas.py` и `rpc/mapping.py` — симметричная пара.

Доменные ошибки (`infra/errors.py`) маппятся в коды транспорта централизованно:
в HTTP — таблицей обработчиков в `main.py`, в gRPC — перехватчиком
`DomainErrorInterceptor`. В методах сервисера нет ни одного `try/except`.

`IntegrityError` из базы тоже в этой таблице и отдаёт 409, а не 500. Для `core` это
запас прочности, но `booking` будет ловить конфликт слотов именно ограничением БД
под гонкой — там это главный путь.

## Проверки состояния

| Эндпоинт | Что означает | Зависимости |
|---|---|---|
| `/healthz` | процесс отвечает | не проверяются |
| `/readyz` | зависимости доступны | `SELECT 1` в БД, пинг брокера |

Разделены намеренно. Если проверять зависимости в liveness, оркестратор начнёт
перезапускать здоровый сервис из-за чужого сбоя. Если не проверять их нигде —
контейнер считается живым при лежащей базе.

`docker-compose.yml` смотрит на `/readyz`.

Пинг брокера активный: `connect_robust` не признаёт соединение закрытым, пока идут
попытки переподключения, поэтому по его флагам судить нельзя — проверка объявляет
обменник пассивно с таймаутом.

## Трассировка

Заголовок `traceparent` (W3C Trace Context) подхватывается из входящего HTTP-запроса
или из метаданных gRPC, живёт в `ContextVar` и проставляется в события, уходящие
в брокер. Битый или отсутствующий заголовок начинает новую трассу, а не роняет запрос.

Благодаря этому событие в RabbitMQ несёт идентификатор трассы того запроса, который
его породил. Без этого события в системе трассировки выглядели бы несвязанными
корнями, и установить, какой запрос породил списание материалов, было бы нечем.

Полноценный OpenTelemetry подключается поверх этого же механизма.

## Запуск

В составе системы:

```bash
docker compose up -d core-service
```

Миграции накатываются на старте контейнера через `docker-entrypoint.sh`.

Локально, без контейнера:

```bash
python -m venv .venv && .venv/bin/pip install -e ".[dev]" -e ../../gen/python
.venv/bin/alembic upgrade head
.venv/bin/python -m app.main
```

REST на `:8001`, gRPC на `:9001`. Включена gRPC-рефлексия, так что `grpcurl`
работает без `.proto` под рукой.

## Инвариант непересекающихся смен

Проверяется дважды: в агрегате `Employee.assign_shifts` (даёт внятную ошибку 409)
и на уровне БД через `EXCLUDE USING gist` (ловит запись в обход приложения).
Смены встык — не пересечение, `tstzrange` полуоткрытый.

Дублирование намеренное: `booking-service` строит на графике решение о занятости
специалиста, и пересекающиеся смены сломали бы его логику.

## Публикация событий

`branch.opened` и `employee.hired` уходят в обменник `mirea.events` в protobuf-JSON,
persistent, с подтверждениями издателя.

Публикация идёт после коммита транзакции, а не внутри неё. Это классический dual
write: если процесс упадёт между коммитом и публикацией, событие потеряется.
Промышленное решение — транзакционный outbox: писать событие в ту же базу одной
транзакцией и отправлять отдельным воркером. Здесь цена такой надёжности не
оправдана, но дыра существует, и о ней стоит знать.

## Тесты

Два вида: unit и интеграционные.

```bash
.venv/bin/python -m pytest          # всё
.venv/bin/python -m pytest tests/unit          # без БД, 0.05s
.venv/bin/python -m pytest tests/integration   # нужен запущенный Postgres
```

**Unit** (`tests/unit/`) — чистая логика без ввода-вывода: инвариант непересекающихся
смен в агрегате `Employee` и кодирование курсора пагинации.

**Интеграционные** (`tests/integration/`) — домен против настоящего Postgres в базе
`core_db_test`. Схема накатывается миграциями, а не `create_all`: так проверяются
и сами миграции. Публикация событий проверяется через `RecordingPublisher`,
брокер для тестов не нужен.

DSN тестовой базы переопределяется переменной `CORE_TEST_POSTGRES_DSN`.
