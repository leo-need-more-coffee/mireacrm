# inventory-service

Склад материалов филиала: списание по факту оказанной услуги, пополнение,
контроль остатков.

| | |
|---|---|
| **Язык** | Go 1.26 + chi + pgx |
| **БД** | PostgreSQL, `inventory_db` |
| **Транспорт** | REST наружу, gRPC-клиент к `catalog`, потребление RabbitMQ, публикация в RabbitMQ и NATS |
| **Порты** | REST :8004 |
| **Автотестов** | 20 |

Первый сервис-потребитель в системе: до него все только публиковали события.

## Ответственность

**Владеет:** остатками материалов по филиалам, историей движений, минимальными
порогами.

**Не владеет:** справочником материалов и нормативами расхода — это
`catalog-service`. Здесь только количества.

## Основной сценарий

```
appointment.completed (RabbitMQ)
  → gRPC catalog.GetConsumptionNorms(service_id)
  → одна транзакция: отметка события в inbox + списание всех позиций
  → publish consumables.written_off
  → если остаток ниже порога:
      publish stock.low (RabbitMQ)  — для отчётов и уведомлений
      publish в NATS mirea.branch.{id}.alerts — мгновенный алерт админу
```

## REST API

| Метод | Путь | Что делает |
|---|---|---|
| `GET` | `/branches/{branch_id}/stock` | Остатки филиала |
| `GET` | `/branches/{branch_id}/stock/low` | Позиции ниже порога |
| `POST` | `/branches/{branch_id}/stock/replenish` | Пополнить склад |
| `PUT` | `/branches/{branch_id}/stock/{consumable_id}/threshold` | Задать минимальный порог |

## Идемпотентность

RabbitMQ доставляет at-least-once, поэтому повторная доставка не должна списать
материалы дважды. Реализован inbox: таблица `processed_events`, обработка
начинается со вставки `ON CONFLICT DO NOTHING`.

**Отметка пишется той же транзакцией, что и списание.** Это не деталь: если
отмечать отдельной транзакцией, упавшее списание оставит событие помеченным, и
повторная доставка молча пропустит его. Проверено на живой системе — одно
событие, доставленное три раза, списывает материалы один раз.

## Списание и пополнение — разные операции

Одним upsert не делаются, и это тонкий момент Postgres:

```sql
CHECK (quantity >= 0)
```

проверяется на **предлагаемой строке до** разрешения конфликта, а `ON CONFLICT`
перехватывает только нарушения уникальности. При списании Postgres увидит
`quantity = -60` в предлагаемой строке и упадёт, не дойдя до `DO UPDATE`.

Поэтому пополнение — upsert (создаёт позицию), списание — `UPDATE ... WHERE
quantity + delta >= 0` (только уменьшает существующую). Списать то, чего на складе
нет, нельзя по смыслу, а не только технически.

Все движения одной транзакции: частично списанный набор материалов хуже, чем
не списанный вовсе.

## Обработка событий

Каркас потребителя — общий, в `libs/go-common/infra/consumer.go`:

- `prefetch = 16` — иначе брокер вывалит всю очередь разом, и при падении процесса
  вся пачка вернётся необработанной
- трасса продолжается из `EventEnvelope.traceparent`, а не начинается заново
- ошибка обработки → `Nack` без повтора → сообщение уходит в `mirea.events.dead`
- ключ без обработчика подтверждается, иначе очередь встанет

Очередь и биндинги объявлены декларативно в `deploy/rabbitmq/definitions.json`,
потребитель их не создаёт.

## Развёртывание

Постоянное соединение с брокером и подписка на очередь означают, что сервис
должен работать всё время. Бессерверный контейнер, который останавливается
между вызовами, для него не подходит: очередь копилась бы, пока его нет.
Поэтому в конвейере он публикуется обычным образом в реестр.

## Запуск

```bash
docker compose up -d inventory-service   # REST :8004
go test ./...                            # 9 тестов, без БД
```

## Тесты

Два вида: unit и интеграционные.

```bash
go test ./...                    # только unit, база не нужна
go test -tags=integration ./...  # плюс интеграционные, нужен Postgres
```

**Unit** — доменная логика на фейках: применение нормативов, идемпотентность,
подъём тревоги в оба брокера, поведение при недоступном каталоге.

**Интеграционные** (11 шт.) — против настоящего Postgres в базе
`inventory_db_test`. Схема поднимается миграциями, а не `CREATE TABLE` в тесте:
так проверяются и они.

Вынесены под сборочный тег `integration`, чтобы `go test ./...` без базы оставался
быстрым, а в CI база поднималась отдельным шагом.

Покрыто то, что фейками проверить нельзя, потому что логика живёт в SQL:
разделение списания с пополнением, отказ списать несуществующую позицию,
откат всего набора при частичной неудаче, транзакционный inbox (упавшее списание
снимает отметку об обработке) и история движений.

DSN тестовой базы переопределяется переменной `INVENTORY_TEST_POSTGRES_DSN`.
