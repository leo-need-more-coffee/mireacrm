# analytics-service

Отчётность по сети: выручка филиалов, загрузка специалистов, расход материалов,
конверсия записей.

| | |
|---|---|
| **Язык** | Python 3.12 + FastAPI |
| **БД** | PostgreSQL, `analytics_db` |
| **Транспорт** | REST наружу, gRPC-клиент к `core`, потребление RabbitMQ |
| **Порты** | REST :8008 |
| **Автотестов** | 30 |

Единственный сервис с биндингом `#`: получает весь поток событий системы.

## Ответственность

**Владеет:** витринами. Собственных бизнес-фактов не создаёт — всё состояние
производное.

**Не владеет:** ничем первичным. Любая цифра выводится из событий других сервисов,
и это принципиально: аналитика не ходит в чужие базы, она слушает шину.

## Витрины

| Таблица | Из каких событий |
|---|---|
| `appointment_facts` | `appointment.created`, `.completed`, `.cancelled` |
| `invoice_facts` | `invoice.issued`, `invoice.paid` |
| `consumable_facts` | `consumables.written_off` |
| `client_facts` | `client.registered` |

Одна строка на сущность, а не на событие: `appointment_facts` хранит жизненный
цикл записи, поэтому конверсия считается группировкой по состоянию, а не
вычитанием счётчиков.

`branch.opened`, `employee.hired` и `stock.low` в витрины не ложатся —
подтверждаются молча, иначе очередь встанет.

## REST API

| Метод | Путь | Что считает |
|---|---|---|
| `GET` | `/branches/{branch_id}/revenue` | Выручка, число счетов, средний чек |
| `GET` | `/employees/{employee_id}/workload` | Записи, завершённые, занятые минуты, комиссия |
| `GET` | `/branches/{branch_id}/funnel` | Записались → пришли или отменили, конверсия |
| `GET` | `/reports/consumables` | Расход материалов по позициям |

Все принимают период через `?from=&to=`.

`GET /revenue` подтягивает название филиала из `core` по gRPC — витрины хранят
только идентификаторы.

## Решения, которые стоит знать

**Время факта берётся из события, а не из момента вставки.** Изначально стояло
`server_default=now()`, и тест это поймал: если аналитика полежит и потом догонит
очередь, все факты лягут на дату обработки, а отчёты за период поедут.

**Выручка считается по оплаченным счетам.** Выставленный счёт — ещё не деньги.

**Занятые минуты — только по завершённым записям.** Отменённая запись время
специалиста не занимала.

**Незавершённые записи не портят конверсию.** В знаменателе только те, чей исход
известен: `completed / (completed + cancelled)`.

**Событие исхода может опередить создание.** Очереди у сервисов разные, порядок
между ними не гарантирован. Если факта записи ещё нет, `appointment.completed`
просто ничего не делает — конверсия досчитается по тем, что создались.

## Идемпотентность

Inbox `processed_events` с отметкой в той же транзакции, что и запись факта.
Повторная доставка не задвоит выручку.

## Запуск

```bash
docker compose up -d analytics-service   # REST :8008
```

## Тесты

Два вида: unit и интеграционные.

**Unit** — конверсия воронки, включая случай без завершённых записей.

**Интеграционные** — против настоящего Postgres в базе `analytics_db_test`:
inbox и снятие отметки при откате, выручка только по оплаченным, средний чек,
воронка по состояниям, исход без создания, занятые минуты, группировка расхода
материалов.
