# notification-service

Связь с внешним миром: напоминания клиентам, алерты администраторам филиала.

| | |
|---|---|
| **Язык** | Go 1.26 + chi |
| **БД** | нет |
| **Транспорт** | REST наружу, gRPC-клиент к `client`, потребление RabbitMQ и NATS |
| **Порты** | REST :8007 |
| **Автотестов** | 10 |

Единственный сервис, который слушает оба брокера сразу.

## Ответственность

**Владеет:** шаблонами сообщений и логикой выбора канала.

**Не владеет:** контактами клиента — они запрашиваются у `client-service` по gRPC
в момент отправки, а не дублируются здесь. Персональные данные лежат в одном
месте.

Единственный сервис без базы. Это осознанно: собственного состояния у него нет,
он только реагирует. Требование «хотя бы один сервис работает с БД» с запасом
закрывают остальные шесть.

Реальной отправки нет — `LogSender` пишет в лог. Подменяется на SMTP или Telegram
Bot API одной строкой в `main`: интерфейс `Sender` для того и заведён.

## Что слушает

**RabbitMQ** — события, на которые нужно отреагировать надёжно:

| Событие | Кому | Реакция |
|---|---|---|
| `appointment.created` | клиенту | Подтверждение записи |
| `appointment.cancelled` | клиенту | Уведомление об отмене с причиной |
| `invoice.issued` | клиенту | Счёт к оплате |
| `stock.low` | администратору филиала | Материал заканчивается |

**NATS** — `mirea.branch.*.alerts`, мгновенные всплывающие алерты на экран
администратора.

Тот же факт про низкий остаток приходит обоими путями: из NATS сразу и без
гарантий, из RabbitMQ надёжно и по шаблону. Это и есть наглядная демонстрация
разницы между брокерами — сервис обрабатывает их по-разному именно потому, что
гарантии разные.

## Выбор канала

Уважает предпочтение клиента, но откатывается на то, что есть: пустой телеграм —
не повод не отправить ничего. Порядок отката: telegram → email → sms.

Администратору филиала личные контакты не нужны, его сообщения уходят в канал
`dashboard` — на экран на ресепшене.

## Что считается ошибкой, а что нет

Разделение принципиальное для потребителя событий:

- **Отправка не удалась** (SMTP лежит) — отправка помечается `failed`, ошибка
  наружу не поднимается. Поток событий важнее одного письма.
- **Контакты недоступны** (`client-service` лежит) — ошибка поднимается, событие
  уходит в dead-letter. Без контактов отправлять некуда, и повторить осмысленно.

## REST API

| Метод | Путь | Что делает |
|---|---|---|
| `POST` | `/notifications` | Отправить произвольное уведомление клиенту |
| `GET` | `/notifications/{notification_id}` | Статус отправки |
| `GET` | `/templates` | Список шаблонов |

`POST /notifications` внутри вызывает `client.GetClientContacts` по gRPC — вложенные
вложенные вызовы.

История отправок — кольцевой буфер на 500 записей в памяти. Своего состояния у
сервиса нет, история нужна только для отладки и проверки; при перезапуске теряется,
и это нормально.

## Каркас

В `infra/` добавился `subscriber.go` — подписчик NATS с разбором protobuf-JSON.
Ошибка разбора только логируется: ронять подписку из-за одного мусорного сообщения
нельзя.

Образ **27.7 МБ** — самый маленький в системе, потому что нет ни драйвера БД,
ни миграций.

## Запуск

```bash
docker compose up -d notification-service   # REST :8007
go test ./...                               # 11 тестов, без внешних зависимостей
```

## Тесты

Только unit — базы нет, интегрировать не с чем. Покрыты выбор канала с откатом,
разделение «отправка упала» и «контакты недоступны», кольцевой буфер истории,
подстановка в шаблоны и вычистка незаполненных плейсхолдеров.
